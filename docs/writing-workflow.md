# 写作与版本管理工作流

## 1 选择任务类型

- **规划**：调整大纲、章节目的、证据需求，不直接把计划写成结论。
- **起草**：根据已登记证据形成段落，优先调用 `nature-writing`。
- **润色**：不改变事实、数值和逻辑，只改善表达，调用 `nature-polishing`。
- **审查**：找出无证据结论、逻辑断裂、变量不一致和对象混淆，先报告问题。
- **定稿**：合并章节、统一引用和格式，调用 `academic-paper-composer` 与 `documents`。

## 2 修改前检查

1. 对应章节的“目的”和“完成判据”是否明确。
2. 需要使用的公式、数据、截图、代码和文献是否已经登记。
3. 本次修改是否会改变大纲、变量定义、方法或结论。
4. 若证据不足，先补证据或降低表述强度，不能生成看似完整但不可验证的内容。
5. 用词优先选择本专业常用表达，减少抽象、重复表述；例如用“混合效果”“结构尺寸”“选择参数时”。必须保留技术含义：功率通常用W或kW表示，能耗表示一定过程消耗的能量，常用J或kWh，两者不能直接替换。

## 3 分支和提交

- 分支：`codex/chapter-编号-主题`，例如 `codex/chapter-5-macro-ui`。
- 提交前缀建议：`写作:`、`证据:`、`图表:`、`引用:`、`代码:`、`结构:`、`修正:`。
- 一次提交只解决一个明确问题，提交信息写结果，不写“更新一下”。

示例：

```text
证据: 登记RBF独立验证数据与误差指标
代码: 完成宏窗口参数校验与外部方程文件写入
写作: 起草5.3.5参数化模型生成流程
修正: 区分理论产量和实际产量定义
```

## 4 修改后同步

- 正文变化：更新对应 `chapters/*.md`。
- 证据变化：更新 `docs/evidence-register.md`。
- 状态变化：更新 `docs/progress.md`。
- 结构、方法或结论变化：更新 `CHANGELOG.md`。
- 用户提出论文修改意见：在 `worklog/index.html` 追加或更新对应条目，记录意见原意、论文位置、处理结果和真实状态。
- 重要修改通过 Pull Request 对比，合并前确认标题、图表编号、引用和变量符号没有失配。


```text

```

## 6 文献入库与正文引用

1. 新文献先保存到 Zotero 的“00 待整理”集合，不得将 PDF 散放在仓库章节目录或 `chapters/` 中。
2. 在 Zotero 查重，再在 `literature/文献总表.md` 分配唯一 `LIT` 编号，并将条目加入主要使用章节集合。
3. 使用 `literature/99-模板/文献卡片模板.md` 记录研究边界、页码摘录和拟插入的论文位置；基础元数据以 Zotero 为主库。
4. 同一文献在 Zotero 只保留一个条目和一份附件；跨章节用途通过多个集合、卡片和 `literature/章节文献地图.md` 表达。
5. 只有标记为“全文已核验”且页码可定位的摘录，才能用于支撑正文事实。
6. 正文引用后，在文献卡片“正文使用记录”和章节索引中同步登记引用位置。

## 7 作者确认稿 Word 汇总与桌面同步

- 仓库主文件：`deliverables/双轴桨叶式混合机大论文_确认稿汇总.docx`；桌面副本：`C:/Users/Administrator/Desktop/双轴桨叶式混合机大论文_确认稿汇总.docx`。
- 只收录作者明确确认的写作内容，按`docs/outline.md`放入对应章节或小标题下；未确认的草稿仍留在章节文件，不自动进入确认稿。
- 每次确认合入后，核对正文、引用与标题对应关系，逐页检查版式，再复制桌面副本并核对SHA256；记录本次确认范围和文件校验值。
- 同步在每次确认合入时执行，不代表持续后台监控。修改前比较两份文件与最近登记的SHA256；发现作者手改或两份内容不同，先保留备份并确认合并来源，不直接覆盖任一版本。
- 作者认可文字不等于研究证据、引用或学校格式全部核验；确认稿汇总不是送审定稿。提交和推送GitHub须有作者明确指令。
